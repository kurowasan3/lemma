# 収益化・SEO の設計

## 0. 前提となる事実

- 【確認】問題データ（問題文・答え・解説・選択肢）は Public リポジトリの `content/`・`data/` にあり、誰でも取得できる。**問題の中身を有料で隠すことはできない**。
- 【確認】アプリの URL はハッシュルーティングで実質1つ（`#ids=…` は検索エンジンから個別ページに見えない）。
- 【確認】問題は「AI 制作」と「最難関大の入試問題の改題」で作られている（管理表の運用。`provenance` の作成方法は公開しない設定 `INCLUDE_METHOD`）。

したがって：**収益の柱は (1) 公開サイトの広告・アフィリエイト、(2) 機能に対する有料会員**。問題の中身は無料のまま、検索からの入口として使う。

## 1. 無料・有料の境界

| 機能 | ゲスト | 同期ユーザー（無料） | 有料会員 |
| --- | --- | --- | --- |
| 全問題の演習・3つの解答形式・ヒント・解説 | ○ | ○ | ○ |
| 復習（間隔反復）・計算トレーニング・グラフ | ○ | ○ | ○ |
| ブックマーク | ○ | ○ | ○ |
| 複数端末の同期 | — | ○ | ○ |
| 公開サイトの広告 | あり | あり | **なし** |
| 学習分析（基本）：分野別の解いた数・正答率・連続日数 | ○ | ○ | ○ |
| 学習分析（詳細）：分野×難易度の定着度の推移、苦手の自動抽出、解答時間の分布、期間比較 | — | — | ○ |
| 学習履歴の保持 | 端末内5,000件 | 端末内5,000件＋サーバー全件 | 同左。**履歴の CSV/JSON 書き出し（全期間）** |
| 学習管理：目標（試験日・1日の問題数）からの計画、自作の問題セット（ブックマークから作成・並べ替え・共有リンク） | — | — | ○ |
| 将来のプレミアム機能（例：類題の自動推薦、模試形式の時間制限セット） | — | — | ○ |

原則（理念。[system-design.md](system-design.md) §0）：**お金がなく参考書すら買えない受験生でも、登録なしで十分に使えること**。有料会員の中心は**広告非表示**で、余裕のある人に運営を支えてもらう形にする。詳細分析・学習管理は「あると便利」な追加分にとどめる。
**学習の効果に直接効く機能（想起・分散・交互練習）は無料に残す**。有料は「見える化」「管理」「便利さ」。受験生の家庭の経済状況で学習効果に差をつけないため、また無料の利用者が多いほど公開サイトと口コミが育つため。

## 2. 広告

### 2.1 配置

| 場所 | 広告 | 理由 |
| --- | --- | --- |
| 公開サイト（www）の問題ページ・分野ページ | AdSense：問題文と「解答を見る」の間に1枠、ページ末尾に1枠 | 検索からの訪問が最も多い場所。読み物として成立する |
| アプリ（app）の演習中 | **なし** | 集中を妨げ、誤タップ（AdSense の禁止事項）を招く。第三者スクリプトをアプリのオリジンに入れない（system-design §2.2） |
| アプリの結果画面・ホーム下部 | 自前のアフィリエイト枠（§3）だけ | 画像と自前のリンクで、外部スクリプトを読まない |

- 【確認】AdSense は iframe 内への設置を禁止しているため、アプリ内で「別オリジンの iframe に広告を隔離する」方法は取れない。
- 【確認】AdSense は `ads.txt` をドメインのルートに置く必要がある → 独自ドメインが前提（`<user>.github.io/<repo>/` では置けない）。
- 利用者の多くが未成年のため、**非パーソナライズ広告を既定**にする（AdSense の設定。【要検証】日本向けの設定方法）。
- 公開サイトのページは静的 HTML なので、広告スクリプトは `async` で読み、本文の表示を遅らせない。

### 2.2 広告の読み込み条件

```
www のページ読み込み
  └─ Cookie `ent`（§4.4）が「有料」なら広告スクリプトを読まない
     それ以外は adsbygoogle.js を async で読む（Cookie の同意バナーは日本向けでは置かない方針。EEA からの閲覧は【要検証】）
```

## 3. アフィリエイト

### 3.1 データ

`content/books.json`（新規・手で管理）：

```json
{ "schema": "lemma.books/1",
  "books": [
    { "id": "bk-taiou-iii", "title": "（書名）", "publisher": "…", "level": [2, 3],
      "fields": ["III-15", "III-16", "III-17"], "tags": ["定積分", "回転体"],
      "links": { "amazon": "https://www.amazon.co.jp/dp/<ASIN>?tag=<ID>", "rakuten": "…" },
      "note": "なぜこの本を勧めるか（運営者の言葉で）" } ] }
```

- `tools/build_app_data.py` が `data/books.json` に、`tools/build_site.py` が公開サイトの分野ページに出す。`data/` の既存形式は変えない（ファイルが1つ増えるだけ）。
- 選ぶ基準を明記する（難易度・分野が合うものだけ。報酬率で選ばない）。

### 3.2 導線

| 場所 | 出し方 |
| --- | --- |
| 公開サイトの分野ページ | 「この分野を補強する参考書」2〜3冊 |
| 公開サイトの問題ページ | 末尾に、その分野の1冊 |
| アプリの結果画面 | 正答率が低かった分野の1冊を、**1セッションに1回まで**、閉じられる形で |
| アプリの設定画面 | 「参考書の紹介」一覧 |

- すべてに「広告」「PR」を表示し、リンクに `rel="sponsored noopener"` を付ける（景品表示法のステマ規制、要法務確認）。
- 有料会員にもアフィリエイト枠は出すか：**出さない**（「広告非表示」の約束に含める方が分かりやすい）。

## 4. 有料会員（Stripe Billing）

### 4.1 構成

```
アプリ（app）                 Supabase Edge Functions                    Stripe
 「有料会員になる」─JWT─►  billing-checkout ─(customer作成/取得)─►  Checkout Session 作成
        ◄──────────────── url ──────────────────────────────────────── (ホストされた決済画面)
 ブラウザが Stripe の画面へ移動 ─────────────────────────────────────►  支払い
                                stripe-webhook ◄──署名つき Webhook──── checkout.session.completed
                                  │                                     customer.subscription.*
                                  │                                     invoice.paid / payment_failed
                                  └─► billing.subscriptions・entitlements を更新（service_role）
 アプリ：GET entitlements（RLS で本人の行だけ）→ 機能を切り替え
 「支払いの管理」─JWT─►  billing-portal ─► Customer Portal の URL（解約・カード変更・領収書）
```

- ブラウザには Stripe の JS を入れない（Checkout・Portal はリダイレクト）。CSP を厳しく保てる。
- 決済画面・領収書・解約・カード変更は Stripe のホスト画面に任せ、自前で作らない（開発・PCI 対応のコストを0に近づける）。

### 4.2 Webhook の処理

| イベント | 処理 |
| --- | --- |
| `checkout.session.completed` | `client_reference_id`（＝`user_id`）と `customer` を `billing.customers` に記録 |
| `customer.subscription.created` / `updated` | `billing.subscriptions` を写し、`entitlements` を `status ∈ {active, trialing}` なら `valid_until = current_period_end`、`past_due` は猶予3日 |
| `customer.subscription.deleted` | `entitlements.status = 'canceled'`（`valid_until` はそのまま＝期間の終わりまで使える） |
| `invoice.payment_failed` | 状態を写すだけ（メールは Stripe の自動メールに任せる） |

- 署名を検証する（`stripe.webhooks.constructEventAsync`、生のリクエスト本文で）。検証できないものは 400。
- `billing.stripe_events(id primary key)` に処理済みの ID を入れ、**同じイベントの二重処理を防ぐ**（Stripe は再送する）。
- Webhook の順番は保証されないので、`subscription` の状態は毎回 Stripe から取り直して上書きする（イベント本文の順序に頼らない）。

### 4.3 権限の判定

```sql
-- アプリが読む（RLS で本人の行だけ）
select service, plan, status, valid_until from public.entitlements;
```

クライアントは「`valid_until > 今` かつ `service in ('lemma','all')`」なら有料機能を表示し、結果を `localStorage` に24時間キャッシュ（オフラインでも有料機能を使えるように）。

**権限をどこで守るか**（重要）：

| 有料機能の種類 | 守り方 | 理由 |
| --- | --- | --- |
| サーバーにしかないもの（全期間の履歴の書き出し、将来のサーバー計算） | **サーバーで判定**（RLS か Edge Function で `entitlements` を見る） | 回避されると実害がある |
| 端末の中だけで完結する表示（詳細な分析画面・計画機能） | クライアントで判定し、**回避されることは許容** | コードは公開されており隠せない。守るコストに見合わない。正規の利用者の体験を優先 |
| 広告非表示 | クライアント（Cookie）で判定 | 回避されても損失は小さい |

### 4.4 公開サイト（www）で広告を消す

アプリ（app）と公開サイト（www）は別オリジンなので、ログイン状態を直接は共有しない。

1. アプリが有料と判定したら、Edge Function `entitlement-token` で**署名つきの短い証明**（`{sub_hash, until}` を HMAC、有効7日）をもらう。
2. アプリが Cookie `ent=<証明>; Domain=<親ドメイン>; Path=/; Secure; SameSite=Lax; Max-Age=604800` を書く（JS から書くので HttpOnly にはできないが、中身は認証に使えない値）。
3. www のページは `ent` があれば広告を読まない（署名の検証はしない。偽造されても失うのは広告1枠の収益だけ）。

ユーザーID そのものは入れない（`sub_hash` は照合用で、www 側では使わない）。

### 4.5 決済とユーザーデータの分離

| 情報 | 置き場所 | 学習データとの結び付き |
| --- | --- | --- |
| カード番号・住所・氏名 | Stripe のみ | なし |
| Stripe の顧客ID・購読ID・状態 | `billing` スキーマ（API に非公開） | `user_id` だけで結ぶ |
| 有料かどうか（期限） | `public.entitlements` | 本人だけが読める |
| 学習記録 | `public.study_*` | 決済の情報を一切持たない |

退会時：`account-delete` が購読を解約 → `delete_my_account()`。`billing.*` は `auth.users` の削除で消える（`on delete cascade`）。会計上の記録は Stripe 側に残る。

### 4.6 価格・プラン（仮説。検証して決める）

| プラン | 価格（税込・仮） | 備考 |
| --- | --- | --- |
| 月額 | 480円 | 受験生が自分で払える額を上限の目安にする |
| 年額 | 3,800円 | 受験期（4月〜2月）をまたぐ前提で約2か月分の割引 |
| 全サービス（Lemma＋Mathel ほか） | 未定 | [mathel-integration.md](mathel-integration.md) |

- 価格は Stripe の Price で管理し、コードに書かない（`billing-checkout` は `price` の lookup_key を受け取る）。
- 無料トライアル（7日）を入れるかは、最初の100人の反応を見て決める。
- 未成年の課金：Checkout の前に「保護者の同意を得ています」の確認を必須にする（要法務確認）。

### 4.7 法令・規約（公開前に必要）

- 特定商取引法に基づく表記のページ（`tokushoho.html`）。個人で運営する場合の住所・電話番号の表示方法は要確認（請求があれば開示する形が認められる条件がある）。
- 利用規約（`terms.html`）：解約・返金・未成年・禁止事項。
- 定期購入の最終確認画面：Checkout の画面で、価格・支払時期・自動更新・解約方法が読めること（Checkout の `custom_text` で補う）。
- いずれも**要法務確認**。この文書は法的助言ではない。

## 5. SEO・集客

### 5.1 公開サイトの構成（www）

`tools/build_site.py`（新規）が `content/` と `data/` から静的 HTML を作る。アプリの `data/` 生成とは独立した**追加の出力**。

```
site/                                   … Cloudflare Pages の www プロジェクトに配置（git には入れず CI で生成）
  index.html                            トップ（分野一覧・アプリへの入口）
  fields/<分野ID>/index.html            分野ページ：説明・難易度別の問題一覧・参考書
  problems/<問題ID>/index.html          問題ページ（4,236件）
  sets/<問題セットID>/index.html         問題セット
  sitemap.xml（＋分割 sitemap-<n>.xml）  robots.txt  ads.txt  og/<分野ID>.png
```

| 要素 | 内容 |
| --- | --- |
| URL | 問題ID をそのまま使う（`/problems/III-INT-515/`）。ID は変えない約束があるので、URL も永続になる |
| `<title>` | `{テーマ}｜{分野}（{難易度}）の問題 III-INT-515｜Lemma 受験数学` |
| 本文 | 問題文（KaTeX をビルド時に HTML にして埋め込む＝JS なしで数式が読める）、答えと解説は `<details>` に入れて最初は閉じる |
| 構造化データ | `BreadcrumbList`（トップ › 科目 › 分野 › 問題）。【要検証】`Quiz`／`LearningResource` の適用可否 |
| `canonical` | 自分自身。アプリの `#ids=` ではなくこちらを正とする |
| OGP | `og:title` `og:description`（テーマ＋問題文の冒頭100字）、`og:image` は分野ごとの画像（`og/<分野ID>.png`、ビルド時に作成） |
| アプリへの導線 | 「この問題をアプリで解く」→ `https://app.<ドメイン>/#ids=<問題ID>`（既存の共有リンクをそのまま使う） |
| 内部リンク | 同じ分野・同じタグの問題、前後の問題 |

### 5.2 何を索引させるか（品質と規約の面）

全問題を一律に公開ページにすると、次の危険がある：
- **大量の AI 生成ページ**は Google の「大量生成コンテンツの不正使用（scaled content abuse）」と判断される恐れがある。
- **入試問題の改題**の扱い（元の問題の著作権）。改題で元の核を抜き出す方針だが、検索で集客すると元の大学・出版社の目に触れる機会も増える（要法務確認）。

方針：
1. `quality.checks.human = true`（人が確かめた問題）だけを `index` にし、それ以外は `noindex`（ページは作るが検索結果に出さない）。`quality` は既に `content/` にある【確認】。
   ただし【確認】2026-11-13 時点で `human = true` の問題は **0問**（管理表由来の 4,236問はすべて `false`、内蔵の61問は項目なし）。
   人による確認（管理表の「検証済み」列・弟テスト記録）を進める作業が、SEO の公開量を直接決める。最初は分野ページと問題セットだけで始める。
2. 問題ページには、運営者が書いた「この問題の狙い」（`idea.tex`、核となるアイデア）を必ず載せ、ページ独自の価値を持たせる。
3. 改題の元が特定できる問題（例：大学名・年度を書いたもの）は載せない。`provenance` の非公開方針（`INCLUDE_METHOD`）を維持する。
4. 分野ページ（約20）と問題セットページを先に公開し、問題ページは段階的に増やす。

### 5.3 PWA と SEO の両立

| 論点 | 方針 |
| --- | --- |
| Service Worker のスコープ | www と app を別オリジンにするので重ならない。www には SW を置かない（静的ページはブラウザのキャッシュで十分） |
| オフライン | アプリ（app）は今まで通り。www はオンライン前提 |
| ハッシュルーティング | アプリは変えない（変えると既存の共有リンク `#set=` `#ids=` と e2e が壊れる）。検索用の URL は www が受け持つ |
| 重複コンテンツ | アプリは `<meta name="robots" content="noindex">`（ログイン画面・個人の記録しか固有の内容がない）。正規の URL は www |
| マニフェスト | app だけに置く。www からは「アプリを開く」「ホーム画面に追加の案内」 |

### 5.4 集客の順番

1. 分野ページ・問題セットページ（数十ページ）を公開して索引させる。
2. 人が確かめた問題から順に問題ページを `index` に。
3. SNS 共有：アプリの結果画面に「この問題を共有」（www の URL。OGP 画像つき）。
4. 効果測定は Cloudflare Web Analytics（Cookie なし）と Google Search Console だけ。
