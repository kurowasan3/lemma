# v0.29.0 候補：主な解法と補助の解法のデータ構造の分離（設計監査）

これは設計監査で、コード・問題・解法カード・管理表・ビルド生成物・学習記録はどれも変えていない（§12）。

- 集計は `collect_stats.py`（このフォルダ。読むだけ）で出した。
  - `stats.csv`：集計の表
  - `problem_states.csv`：全5,216問の状態
- 調べた時点の main：d525360（v0.28.3）

## 1. 現行仕様（コードで確かめたこと）

### 1.1 データの流れ

```
管理表 .xlsx ─(tools/xlsx_to_content.py)→ content/problems/*.json の techniques（「解法」列の名前・ID の並び）
content/techniques.json（カード：tags・weak）  ┐
content/problems/*.json（tags・techniques）    ┴(tools/build_app_data.py の select_techniques)→ data/techniques.json
data/techniques.json ─(js/catalog.js loadTechniques)→ byProblem：問題ID → [{id, main}]
                                                     ─(js/mastery.js)→ 習熟・転用・推薦の候補
                                                     ─(js/app.js)→ 解法チップ・解法ページ・想起の質問・類題
```

### 1.2 依頼の9項目への答え

1. **主な解法の決め方**は、`select_techniques`（tools/build_app_data.py）による。
   - `techniques` が空：タグを正規名にし、各カードの tags に当たった順で、weak でない最初のカードを主にする。
   - `techniques` が `["主な解法なし"]`：主は無い。
   - それ以外：先頭を主にする。
2. **補助の解法の決め方**も同じ関数による。
   - 自動の問題：タグに当たったカードのうち、主以外のすべてが補助になる（weak も含む）。
   - 名前の指定のある問題：2番目以降が補助になり、タグは使わない。
   - 「主な解法なし」の問題：タグに当たったカードすべてが補助になる。
3. **自動と明示の区別**は data/techniques.json の2つの一覧で表す。
   - `manual`：名前を指定した問題
   - `nomain`：「主な解法なし」を指定した問題
   - どちらにも無い問題が自動。
   - 画面は `manual` に無い問題に「（自動）」を出す（js/app.js techChipsHTML）。「主な解法なし」の問題は補助がタグからなので、「（自動）」と出る。
4. **`nomain` の扱い**
   - 設定する場所：ビルド（select_techniques が 'none' を返したとき）。
   - 参照する場所：tools/audit_techniques.py（主が無いこと・索引にあること・`manual` と重ならないこと）、tests/technique_links_test.py。
   - アプリ（js/）は読んでいない。
5. **主な解法の無い問題の表し方**：data/techniques.json のどのカードの `main` にも問題IDが無いこと。それだけで、明示の「主なし」と自動の「主なし」の違いは `nomain` でしか分からない。
6. **補助の順序**
   - content の `techniques` の並びは、ビルドでは先頭（主）を決めるためだけに使う。
   - 出力（カードごとの `ids`・`main` は問題IDの順に並べたもの）には、問題ごとの並びが残らない。
   - 画面の並びは「主が先、あとは content/techniques.json のカードの順」（catalog.js の byProblem）。
   - **管理表の「解法」列の2番目以降の並びは、今はアプリのどこにも効いていない。**
7. **習熟・推薦・学習記録の集計の基準**は js/mastery.js techMastery。
   - 学習記録（state.log の各行：p 問題ID・t 時刻・g 評価・r 想起・k）のうち、カードの `ids`（主＋補助）の問題の記録を数える。
   - 得意度：重みは主1・補助0.5（×難易度の係数）。
   - 「完答・知らされずに完答・最近の失敗・直近2回の失敗」は、主と補助を区別せずに数える。
   - 転用の判定と転用の問題の候補は、主の問題だけを使う。
   - 推薦の出題（catalog.js pickToday の fromTech）も主の問題だけ。
   - 想起の質問（app.js recallMain）は、その問題の主な解法について聞く。主が無ければ聞かない。
8. **管理表の「解法」列の読み方**（tools/xlsx_to_content.py）
   - 見出し「解法」の列を、読点・カンマで分けて `techniques` に入れる。空欄なら `techniques` を作らない。
   - 名前の照合はビルドで行い、無い名前は検査（tools/audit_data.py）で誤りになる。
   - **content から管理表へ書き出す処理は無い**（tools/ に無いことを確認）。
9. **既存の問題IDや学習記録との依存**
   - 学習記録・復習状態（pstat）・ブックマークは、どれも問題IDで持つ。解法カードのIDは持たない（js/store.js）。
   - 同期（js/sync.js・supabase/）にも、解法の結びつきは入っていない。
   - 例外1：記録の `r`（想起）には解法IDが無く、「その時点の主な解法」についての答えとして暗に結びついている。主が変わると、過去の `r` は新しい主の想起として数え直される。
   - 例外2：`k:'t'`（解法カードから始めた演習）も、どのカードから始めたかを持たない。
   - 内蔵問題（js/content.js の61問）は別の仕組みを使う。`cards` の配列（先頭が主）と state.cards（カードごとの復習状態）で、data/techniques.json には入らない。今回の対象外。

## 2. 現行構造の問題点

1. **主なし・補助ありを明示できない**。状態D（主なし・補助1つ以上）は、データ上はもう表せている（自動で370問）。しかし管理表から作れるのは、次の2つだけ。
   - 「主な解法なし」＋タグ由来の補助
   - 先頭が主の並び

   「主を空にして、補助をこれと指定する」ことができない。A-GEO-017・I-TRI-081・II-GEO-254 は、今も状態Dではある。ただし、その補助は weak のタグ「接線の長さ」による「接線」で、v0.28.1 の判定では「接線」は誤りだった。必要なのに付けられないのは `circle-tangent` の方。
2. **意味が位置で決まる**。「先頭が主」「予約語は単独」という並びの規則に、主と補助の2つの意味が入っている。どの列を見ても、主・補助・自動のどれかを直接読めない。
3. **「主な解法なし」だけ、補助がタグから来る**（名前の指定ではタグを使わない）。明示の指定なのに自動が混ざり、画面の「（自動）」の表示とも合わない。
4. **補助の並びがアプリに伝わらない**（§1.2 の6）。content と管理表の並びは見かけだけになっている。
5. **管理表に「解法」列が無いまま取り込むと、指定が消える**（v0.28.2 の監査で確認、今も同じ）。取り込みは警告しない。
6. **想起の記録 `r` が解法IDを持たない**ので、主を変えると過去の記録の意味が変わる（§1.2 の9）。

## 4. 設計案の比較

### 案A：今の並びを広げる
`techniques` の並びのまま、`["主な解法なし", "円の接線と半径", …]`（先頭が予約語なら主なし、残りが補助）を許す。

### 案B：主と補助を別の項目に分ける
content の問題に2つの項目を置く。
- `technique_main`：カードIDか名前。`null` は明示の主なし。項目が無ければ未指定。
- `technique_support`：カードの並び。

管理表は「主な解法」「補助の解法」の2列にする。どちらかの列に値がある問題は明示の指定で、タグを使わない。どちらも空なら今と同じくタグから自動。

### 案C：結びつきを1つのオブジェクトにまとめる
`techniqueAssignments: {"main": null, "supporting": [...], "source": "manual"}` のように、出どころも含めて1つの項目にする。

### 比較

| 観点 | 案A | 案B | 案C |
|---|---|---|---|
| データの明確さ | △ 位置で意味が決まる。予約語が名前の並びに混ざる | ○ 項目名で主と補助が読める。「未指定」と「なし」も区別できる | ◎ 出どころまで1か所に入る |
| 実装コスト | ◎ select_techniques と検査の条件を変えるだけ | ○ 取り込み・スキーマ・ビルド・検査・テスト（js は変えない） | △ 案Bに加えて入れ子の扱い。管理表の平らな列との変換が増える |
| 既存コードへの影響 | 最小 | tools/ とテストだけ。data/techniques.json の形は変えない | 同左＋スキーマの入れ子 |
| 管理表との互換 | ○ 1列のまま | ○ 2列に分かれる。旧「解法」列も読める | △ 2列から組み立てる。`source` は管理表に置けない（自動は管理表に書かないため） |
| 自動との整合 | △ 「主な解法なし」だけタグを使う例外が残るか、残さないかを予約語ごとに決める必要 | ○ 「どちらかの列に値があれば明示、タグは使わない」の1つの規則 | ○ 同左 |
| 習熟・推薦への影響 | なし（data の形が同じ） | なし（同左） | なし（同左） |
| Supabase との互換 | 影響なし | 影響なし | 影響なし |
| 将来の拡張 | △ 「補助のうち重要なもの」などを足すと、位置の規則が増える | ○ 項目を足せる（例：`technique_note`） | ◎ オブジェクトの中に足せる |
| 移行で壊すリスク | 低（形が同じ） | 低〜中（一度だけ変換。data が変わらないことを機械で確かめられる） | 中（変換が2段） |
| テストのしやすさ | ○ | ◎ 項目ごとに確かめられる | ○ |

### 推奨：**案B**

- 主と補助を独立に持ち、「未指定（自動）」と「明示の主なし」を区別する、という今回の目的を、規則1つで満たす。規則：どちらかの列に値があれば明示、タグは使わない。
- アプリが読む data/techniques.json の形（カードごとの `ids`・`main`、`manual`・`nomain`）は、状態Dをもう表せている（自動の370問）。そのため、js/・学習記録・Supabase を変えずに済む。
- 管理表の平らな列とそのまま対応する。案Cの `source` は、ビルドで決まる値（`manual`・`nomain` と同じ）なので、content に持たせる必要がない。
- 案Aは安いが、「位置で意味が決まる」という今の問題点（§2 の2）を残す。

## 5. 推奨するデータ構造（案B の詳細）

**content/problems の問題（任意の2項目）**

| 項目 | 値 | 意味 |
|---|---|---|
| `technique_main` | 項目なし | 主は未指定 |
|  | `null` | 主な解法なし（明示） |
|  | `"circle-tangent"`（ID。名前も可） | 主な解法 |
| `technique_support` | 項目なし | 補助は未指定 |
|  | `[]` | 補助なし（明示） |
|  | `["law-sin-cos", …]` | 補助の解法（並びを保つ） |

**決め方**

| technique_main | technique_support | 結果 | 状態 |
|---|---|---|---|
| 項目なし | 項目なし | 今と同じく、タグから自動（weak 以外の最初が主、当たったすべてが結びつく） | 自動のA〜D |
| `"X"` | 項目なし・`[]` | 主X、補助なし | A |
| `"X"` | `[Y, Z]` | 主X、補助Y・Z | B |
| `null` | 項目なし・`[]` | 主なし、補助なし | C |
| `null` | `[Y]` | 主なし、補助Y | **D** |
| 項目なし | `[Y]` | 誤り（主を決めていない。`null` か名前を書く） | — |

**守る条件**（ビルドと tools/audit_data.py で検査し、誤りなら止める）

- 主は0か1つ。
- 補助の中に主と同じカードを書かない。
- 補助の中に同じカードを2回書かない。
- 無いカード（名前・ID・旧ID のどれでもない）を書かない。
- 予約語「主な解法なし」をカード名に使わない（今と同じ）。

**data/techniques.json**：形は変えない。

- カードごとの `ids`・`main`、全体の `manual`（明示の指定のある問題）・`nomain`（明示の主なし）。
- 状態Dの問題は、`ids` にだけ入り、`main` には入らない（今の自動のDと同じ表し方）。
- `manual` と `nomain` の意味は少し変わる。
  - `manual`：主・補助のどちらかを指定した問題。
  - `nomain`：`technique_main` が `null` の問題。`manual` にも入る。
  - 今の「`nomain` と `manual` は重ならない」という検査は、この意味に合わせて直す。
- 補助の並びを画面で使うかは、決めることの一つ（§11）。使う場合は、data に問題ごとの並び（例：`order: {問題ID: [カードID…]}`）を足す。

## 6. 管理表との互換

| 方法 | 内容 | 評価 |
|---|---|---|
| 今の「解法」列を残す | 1列に主と補助を並べる（案A） | 主なし・補助ありが位置の規則になる |
| **「主な解法」「補助の解法」に分ける** | 「主な解法」：空欄＝未指定、`主な解法なし`＝明示の主なし、名前＝主。「補助の解法」：読点区切り、空欄＝未指定 | **推奨** |
| 主なしを明示 | 「主な解法」に `主な解法なし` | 今の予約語をそのまま使える |
| 補助だけを登録 | 「主な解法」に `主な解法なし`、「補助の解法」に名前 | 誤って主が付かない（主の列を空にすると誤りで止まる） |
| 旧形式を読む | 「解法」列があり新しい2列が無い管理表は、`[X, …]` を主X・補助…、`[主な解法なし]` を主 `null` に変換して読む | 移行の期間に必要 |
| 新形式から旧形式へ書き出す | 今は書き出す処理が無い。作るなら A・B・C は書けるが、D は旧形式で表せない | 書き出せない問題を一覧にして止める（黙って落とさない） |

**消えない・誤って付かないための約束**

- 取り込むとき、content に明示の指定がある問題について、管理表に「主な解法」「補助の解法」「解法」のどの列も無ければ、取り込みを止める。今は黙って消える。
- 管理表の元のファイル・復旧版・v0.28.2／v0.28.3 のコピーは上書きしない。移行は新しいコピーを作って行う。
- 列は見出しの名前で探すので、位置は問わない（今と同じ）。

## 7. 学習記録・習熟・推薦への影響

| 項目 | 今 | 案B にしたとき |
|---|---|---|
| 問題を解いたとき、どのカードの習熟が動くか | カードの `ids`（主＋補助）に入るすべてのカード | 同じ。状態Dの問題は、補助のカードにだけ効く（今の自動のDと同じ） |
| 主と補助の区別 | 得意度の重みだけが違う（主1・補助0.5）。完答・失敗などの数え方は区別しない。転用・推薦の出題・想起は主だけ | 変えない |
| 補助だけの問題の集計 | 補助のカードの得意度に重み0.5で入る。転用・推薦の出題には使わない。想起は聞かない | 同じ |
| 推薦の順位 | 主の問題の数（新しい解法の順）と主の問題からの出題 | 変わらない |
| 忘却・復習 | 問題ごとの pstat（問題ID）と、カードの「最近の失敗」（ids の問題） | 同じ |
| 学習記録の読み込み・ローカル保存 | 問題IDだけで持つ | 変更なし。移行も不要 |
| Supabase 同期 | 結びつきを送らない | 変更なし |
| 過去の記録の移行 | — | **不要**（データの結果が同じなら、どの数字も変わらない） |

**影響が出るのは、あとで結びつきを変えたとき**（移行そのものでは出ない）。

- 例：3問に `circle-tangent` を補助として付けると、そのカードの得意度・最近の失敗に3問の記録が入る。
- 主を変えると、`r`（想起）の意味も変わる（§2 の6）。これは今もある性質で、案Bでは変わらない。

**主と補助の重みについての意見**

- 今の「得意度は補助0.5」は妥当。問題を解いても、補助の解法を使ったとは限らないため。
- 一方で、「直近2回の失敗」と「最近の失敗」は補助の問題でも数えている。補助のカードが、主でない問題の失敗だけで「要復習」になりうる。習熟の算法は今回変えないが、状態Dの問題を増やすと、この影響も増える。補助の問題を「要復習」の判定から外すかは、別に検討する価値がある（§10）。

### 一括と段階の比較

- **一括**：44問の変換・取り込み・ビルド・検査を1つの版で行う。版が1つで済むが、確かめる範囲が広い。
- **段階（推奨）**
  1. **v0.29.0**：新しい2項目と2列を読めるようにし、旧 `techniques` も読む。44問を新しい項目に変換する。**data/techniques.json が変換前と同じこと**を確かめる（dataVersion を除いて同じ）。結びつきは何も変えない。
  2. **v0.29.1**：状態Dの明示指定を使う。今回の3問に、主 `null`・補助 `circle-tangent`（今の補助「接線」は v0.28.1 の判定で誤りだったので、残すかを決める）。
  3. **v0.29.2**：管理表の旧「解法」列と旧 `techniques` の読み込みをやめる。管理表の新しいコピーが正本になってから行う。
- 段階にする理由：1 で「意味を変えない移行」と「結びつきを変える修正」を分けられる。移行が正しいことを、データが変わらないことで機械的に確かめられる。

## 10. リスクと未解決事項

- **想起 `r` が解法IDを持たない**：主を変えるたびに、過去の想起の意味が変わる。案Bでも変わらない。解く時点の主な解法IDを記録に残す（例：`rt`）かは別の課題で、学習記録の形を変えるため慎重に決める。
- **補助の問題で「要復習」になる**：状態Dの問題が増えると、補助だけの問題の失敗でカードが要復習になる場面が増える（§7）。
- **自動の状態D 368問**：weak のタグだけで補助になっている。正しいかは個別には確かめていない。今回の3問の補助「接線」は、v0.28.1 の判定では誤り。
- **補助の並び**：アプリに伝わっていない（§1.2 の6）。並びに意味を持たせるか、未決。
- **内蔵問題（61問）**：別の仕組み（`cards`、先頭が主）。今回の構造に合わせるかは未確認（対象外）。
- **管理表の書き出し**：書き出す処理が無く、管理表と content の一致は、毎回の照合（spec_check）頼み。
- **未確認**：Supabase のサーバー側（supabase/）は、ファイル（guard.sql など）を読み、解法の結びつきを扱っていないことだけ確かめた。実際のサーバーのデータには触れていない。

## 11. 実装を始める前に決めること

1. **項目名**：`technique_main`／`technique_support` でよいか。
   - content の既存の項目は英語の小文字（`techniques`・`methods`・`tags`）。
   - 管理表の列名は「主な解法」「補助の解法」でよいか。
2. **「主な解法なし」の問題の補助をどうするか**：移行で、今のタグ由来の補助を `technique_support` に書き写すか（データは同じになる）、書かずに補助なしにするか（II-GEO-212・III-DIF-131 から「接線」が外れる）。推奨は書き写す（移行では意味を変えない）。
3. **状態Dの3問の補助**：今のタグ由来の「接線」を残すか、`circle-tangent` だけにするか。
4. **補助の並び**：画面で使うか。使うなら data に問題ごとの並びを足す（形が少し変わる）。
5. **一部だけ指定した場合**：主だけ・補助だけの指定（片方が未指定）を、誤りにするか、未指定の側をタグから補うか。推奨は誤り（明示と自動を混ぜない）。
6. **段階移行の版の分け方**：§8 の3段階でよいか。

---

**結論**：案B（主と補助を別の項目・別の列にし、どちらかを書けば明示、タグは使わない）を推奨する。

- アプリが読むデータの形は、状態Dをもう表せている。そのため、移行で変わるのは取り込み・ビルド・検査・テストだけ。
- 学習記録・習熟・推薦・同期は変わらず、過去の記録の移行も要らない。
- 「中心の解法」と「理解に役立つ関連解法」を、名前のついた別々の項目として持てる。今回の3問も、主 `null`・補助 `circle-tangent` として素直に書ける。
