# 問題IDの運用（今後の管理表とアプリの同期）

いまの運用（Excel の管理表 → content/ の JSON → data/、Vanilla JS のアプリ）を変えずに、必要な安全策だけを足す案。実装はまだしていない。

## 1. 規則

1. **問題IDは不変。** 一度付けた ID は、問題文を直しても、分野を移しても変えない（data-spec.md の規則を管理表にも適用する）。
2. **削除済みの ID は再利用しない。** 管理表で行を消さない。使わなくなった問題は「状態」の列で表す。
3. **ID が同じなら同じ問題。** 誤りの訂正・表記の修正・解説の改善は同じ ID のまま。数値や条件を変えて別の問題にするとき（改題）は新しい ID を付け、元の ID を「改題元」に書く。
4. **新しい問題の ID はアプリの使用済み ID と照らして付ける。** 追加用の管理表を作るときに、content/ と Git の履歴で使われた最大の番号の次から付ける（ID対応シートでの付け替えを不要にする）。
5. **学習記録は問題 ID に結びついたまま。** ID を変える必要が出たときだけ、旧→新の対応表と記録の移行（端末・バックアップ・Supabase。LM007 と両立する手順）をまとめて行う。

## 2. 管理表に足す列

| 列 | 値 | 用途 |
|---|---|---|
| 状態 | 公開／非公開／統合／要判断 | 行を消さずに外す。非公開・統合はアプリで `quality.status = hidden`（学習記録は残る） |
| 統合先ID | 問題ID | 「統合」のとき、残す方の ID |
| 改題元ID | 問題ID | 改題で新しい ID を付けたとき、元の ID |

## 3. 取り込み前の検査（import_xlsx.py の --check を強める案）

`--check` は今も一時フォルダで作り直して比べるだけなので、ここに次の判定を足す。どれかが 0 でなければ、`--check` なしの取り込みを止める。

| 検査 | 判定 | 止める理由 |
|---|---|---|
| 消える ID | content/ にあって管理表に無い ID | 学習記録の問題が消える（非公開にするなら「状態」の列で） |
| 同じ ID で別の問題 | 正規化した問題文の類似が低い（例：0.5 未満）か、答えも問題文も変わった | 学習記録が別の問題に付く |
| ID の重複 | 管理表の中で同じ ID が2行 | 取り込み結果が行の順で変わる |
| 過去に使った ID の再利用 | 新しい ID が Git の履歴にある | 古い学習記録が新しい問題に付く |

- 警告にとどめるもの：同じ ID で問題文が少し変わった（表記・訂正）、答え・解説だけ変わった。差分レポートに一覧を出し、人が確かめる。
- 判定に使う正規化と類似度は、今回の `match.py` の `n2`・`sim` と同じものを使う（新しい仕組みは作らない）。
- 学習記録の点検（store.js）は今のまま：ID が消えたら「今の問題データに無い問題ID」の警告。

## 4. 差分レポート（取り込みのたびに残す）

`--check` の出力に次の件数を必ず出す：増える ID・消える ID（0 のはず）・同じ ID で内容が変わる問題（訂正／要確認に分ける）・状態が変わる問題。レポートは `docs/import/日付.md` に残し、Git で履歴を追えるようにする。

## 5. 実装の順番（必要最小限）

1. 管理表に「状態」の列を足し、行を消す運用をやめる（Excel の作業だけ）。
2. `import_xlsx.py --check` に §3 の4つの検査と §4 の件数を足す（Python のみ。データ構造は変えない）。
3. 新しい問題の ID の採番を、`plan_rename.py` と同じ規則で行う小さな関数にする。
