**この調査は読み取りだけで行った。** 問題ID・content/・data/・Supabase・学習記録・ブックマーク・メモは変えていない。
照合の相手は v0.27.1 で受け取った管理表（4,913行、受け取ったままのバックアップ）。

## 1. 結論

- **アプリの問題IDは、初回のコミット（2026-11-10）から一度も付け替えられていない。** 問題は足されただけで、消えた ID・別の問題に移った ID はない（Git の全コミットで確認）。
- **ずれたのは管理表の側。** 原因は2つで、どちらも問題内容の照合で裏付けられた。
  1. **10-30 作成の問題の削除と、後ろの ID の詰め直し（588問）**。アプリの元になった管理表（2026-11-03 に書き出し）には 10-30 作成の問題が各分野にあった。いまの管理表ではそのうち 558問（各分野 約30問）が無く、同じ分野でそれより後ろの問題の ID が 約30 ずつ前に詰められている（例：アプリの A-COM-268〜 は管理表の A-COM-238〜）。
  2. **管理表2〜4の ID の付け替え（574問）**。管理表2〜4は、詰めた後の管理表の番号に続けて ID を付けていた。アプリに足すときに既存の ID とぶつかったので、アプリでは別の ID にした（各ファイルの「ID対応」シートに記録がある）。管理表には付け替える前の ID のまま入っている。
- 加えて、管理表には 2026-11-22 作成の新しい問題が 254問ある（アプリには未収録）。うち **190問は、アプリで別の問題が使っている ID** を持つ。
- この結果、同じ ID が別の問題を指す組が 1,352 ある。管理表をそのまま取り込むと、その ID の学習記録が別の問題に付く。

## 3. 照合の方法

ID は使わず、問題内容だけで照合した。

1. 問題文の正規化（空白・改行を無視 → 表記の揺れを無視：`\mathrm`・`\text`・`\displaystyle`・`\dfrac`→`\frac`・`\left`/`\right`・空白命令・全角/半角の句読点・波括弧・`$`）。数値・条件・演算子は変えない。
2. 正規化した問題文が一致する組を候補にする。同じ問題文が複数あれば一意に決めない（F）。
3. 一致しなければ、4文字の重なりで候補を絞り（同数は ID 順で、実行ごとに結果が変わらないようにした）、問題文の類似度を出す。**類似度だけでは確定しない**（E・F・G は人の確認が要る）。
4. v0.27.0 でアプリ側だけ直した列は、fixes.csv の「修正前」の値で照合した（管理表の値は修正前と一致）。
5. 確認：G の問題と同じ解説の行は管理表に無く、対応先の無い管理表の行と同じ解説の問題もアプリに無い。

## 5. 学習記録への影響

学習記録は**問題IDだけ**で問題に結びついている。問題内容の照合用の値は持っていない。

| 記録 | キー | ID が別の問題を指すようになったとき |
|---|---|---|
| 解答の記録 `log` | `p`（問題ID） | 過去の解答が別の問題の記録になる |
| 復習状態 `pstat` | 問題ID | reps・lapses・last・S・D がそのまま別の問題に付き、復習予定もそれで決まる |
| 習得状態（解法カード） | log から計算 | 問題ID→解法の結びつけで数えるので、別の解法の習熟に数えられる |
| ブックマーク `bookmarks` | 問題ID | 別の問題に付く |
| 説明のメモ `explains` | 問題ID | 別の問題のメモになる |
| Supabase `lemma_state.state` | 上と同じ JSON | 同じ。guard.sql（LM007）はキーが消える書き込みを拒むので、ID を付け替える移行は拒まれる |
| ローカルのバックアップ | 上と同じ JSON | 同じ |

- ID が消えた場合は、記録の点検で「今の問題データに無い問題ID」の警告になるだけで、記録は残る。
- **ID が同じまま中身が変わった場合は、どこでも検出されない。** これがいちばん危ない。管理表をいまのまま取り込むと 1,352 の ID がこれに当たる。
- 将来 ID を変えるなら、旧 ID→新 ID の対応表と、学習記録（端末・バックアップ・サーバー）をまとめて書き換える移行が要る。サーバーの保護（LM007）とも両立させる必要がある。今回は作っていない。

## 6. 正本の判断材料

| 観点 | アプリ（content/） | 管理表（受け取った 4,913行） |
|---|---|---|
| 網羅性 | 5,217問。管理表2〜4の追加分をすべて含む | 4,913行。10-30 作成の 558問（対応先なし 493・類題 65）が無い。11-22 の新しい 254問がある |
| 内容の新しさ | v0.27.0 の修正 25問を含む | 11-22 の新しい問題を含む。v0.27.0 の修正は含まない（コピーには24問を反映済み） |
| ID の安定性 | 初回から付け替え・削除なし | 詰め直しと付け替えが起きている。新しい問題の190問は既存のアプリ ID と重複 |
| 学習記録との整合 | 記録はこの ID に結びついている | 1,352 の ID が別の問題を指す |
| 運用の履歴 | Git で全変更を追える | 変更の履歴が無い（詰め直しの時期・理由が分からない） |
| 再生成の安全性 | — | いまのまま取り込むと、1,352 の ID の記録が別の問題に付き、558問が消える（ID としては368が消え、残りは別の問題に使われる） |

**推奨：問題の「同一性」（ID）の正本はアプリ（content/）とする。** 管理表は ID をアプリに合わせてから、問題文などの編集の場として使う。
理由：アプリの ID は付け替えも削除も一度も無く、学習記録がこの ID に結びついている。管理表の ID は少なくとも2回、ずれる操作を受けている。

管理表をアプリに合わせるときに人が決めること：

1. **D 1,162問**：管理表の ID を id_mapping.csv の app_id に書き換える（内容は一致しているので機械的にできる）。
2. **G 493問（10-30 作成）**：管理表から消したのが意図した削除か。意図した削除なら、アプリで非公開にするか（ID は欠番として残し、学習記録は消さない）。誤って消えたなら管理表に戻す。
3. **E 65問（管理表から消えた類題 61・v0.27.0 で直した問題の類題 4）**：上と同じ判断。多くは「似た問題がもう1問ある」ので、重複の整理として残すか決める。
4. **E 6問（言い回しの違い）**：どちらの文を残すか。
5. **11-22 の新しい 254問**：アプリで使っていない新しい ID を付ける（190問は既存のアプリ ID と重複しているので、そのままでは使えない）。

## 7. 今後の安全な同期方式（設計案。今回は実装しない）

1. **問題IDは不変の識別子**とし、一度使った ID は削除しても再利用しない（欠番として記録する）。管理表で ID を詰め直さない。
2. **ID と内容を別に確かめる**：content/ に問題ごとの内容の照合用の値（問題文・答えから作る）を持ち、取り込み時に「同じ ID で内容が大きく変わった」問題を警告して止める。軽い修正（表記・誤りの訂正）と別の問題への入れ替えを区別する。
3. **追加・削除・統合・改題を明示する**：管理表に「状態」列（公開・非公開・統合先 ID・改題元 ID）を置き、行を消して表現しない。
4. **新しい問題の ID はアプリの採番に合わせる**：追加用の管理表は、取り込む前に content/ の使用済み ID と照らして採番する（今回の「ID対応」の作業を不要にする）。
5. **取り込みの差分レポートを標準にする**：`import_xlsx.py --check` の出力に、消える ID・増える ID・同じ ID で内容が変わる問題の数を出し、0 でなければ取り込まない。
6. **学習記録を問題の永続 ID に結びつける**ことは今のまま。ID を変える必要が出たら、旧→新の対応表と記録の移行を一緒に行う。
